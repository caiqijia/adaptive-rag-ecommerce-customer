Design Motivation

固定 pipeline 的浪费，是看不到的浪费

「在吗」也要走一次向量检索 + 精排？标准 FAQ 明明有审定答案，却让 LLM 现场生成？ 多跳问题只检索一次，必然答不全。Adaptive 的第一步不是优化检索，而是决定要不要检索。

固定流水线 Baseline

  • 所有 query 一律 向量召回 → 生成，寒暄也要付检索时延
  • FAQ 不设专用通道，标准答案被重新生成，质量不可控
  • 单一检索粒度，复合问题只召回一半证据
  • 无置信判断，证据不足也照常作答，幻觉直接暴露给用户
  • 越界请求没有边界，「把价格改成 1 元」也会被认真回答

Adaptive 分治 本系统

  • Router 先分类：该省的时延直接省掉，A/E 类零检索
  • FAQ 语义命中（余弦 ≥ 0.85）一次 embedding 直出，零 LLM 调用
  • D 类先拆解子问题 → 分头检索 → 合并证据 → 统一精排
  • 检索层低置信自省 + 生成层 Critic 溯源校验，双拒答防线
  • E 类合规拒答 + 转人工，错误请求不进入生成
Router · 五分类

分类不是目的，路径分治才是

每一类都有独立的处理路径与成本策略。Router 使用低温 0.1 保证确定性，解析失败时降级为 C 类单跳，绝不因路由异常影响可用性。

Retrieval Pipeline

两路召回，只比排名，不比分数

BM25 与向量召回的分数不可比：BM25 无上界，cosine 在 0~1。任何线性加权都等于把决策权交给量纲更大的一方，因此只用排名做 RRF 融合。

①

检索层 · 低置信自省

拦截「证据本身不够」。rerank top1 低于阈值 < 0.3 时先改写再检索，避免拿无关 chunk 强行生成。

②

生成层 · Critic 溯源校验

拦截「证据够、答案却没被支撑」。逐条比对事实陈述与引用 chunk，不通过则改写重试或拒答。

∅

故障降级 · Fail-open 可观测

Critic 故障时放行并打标，降级写入 trace 的 degraded 字段。任何降级都必须显式可见。

Tech Choices

每一项选型都说明「为什么是它」

RAG 不是堆砌最新技术，而是按需求做合理选型，并清楚知道规模上限之后该换成什么。

LLM / Embedding

qwen3.5-flash

国内可直连、免部署，flash 定位低成本，Router / 生成 / Critic 全链路覆盖。规模上来可换私有化 vLLM。

向量库

ChromaDB

本地持久化、零服务依赖，单机 demo 到百万 chunk 都够用；分布式阶段换 Milvus / Qdrant。

关键词检索

rank_bm25 + jieba

纯内存即插即用，与向量缺陷互补：精确匹配专名与数字。十万级以上换 Elasticsearch。

融合算法

RRF · k=60

两路分数量纲不可比，只用排名比，无需调权重；有大量点击数据后再考虑学习式融合。

精排

BGE-Reranker-v2-m3

cross-encoder 精细打分，补上 RRF 丢失的细粒度相关度；可换云端 Rerank API 降本。

Web / 存储

FastAPI · SSE · SQLite

原生 async 与 StreamingResponse，流式零额外依赖；Tortoise 异步 ORM 与 FastAPI 同生态，单机零维护。

Engineering Decisions

八个值得被追问的设计决策

面试里最容易被打穿的地方，往往不是「用了什么」，而是「为什么不换一种」。

01为什么用 RRF，而不是加权融合两路分数？

BM25 无上界、cosine 在 0~1，任何线性加权都等于把决策权让给量纲更大的一方。排名是跨系统唯一可比的尺度，且无需调权重。

02为什么 RRF 用 chunk_id 而不是 doc_id 做主键？

同一文档的不同 chunk 是独立证据，必须独立计分。用 doc_id 会互相覆盖合并，等于丢掉文档内部的相关度区分。

03为什么需要两道拒答防线？

检索层拦截「证据本身不够」，生成层拦截「证据够但答案没被支撑」。两层故障模式不同，缺一不可；考核必须同时看正确拒答率与误拒率。

04为什么 FAQ 用语义匹配而不是让 LLM 判断？

高频标准问题只需一次 embedding（实测 150-300ms）即可直出，零 LLM 调用；标准答案人工审定，质量可控。瓶颈在 embedding 网络往返而非余弦计算。

05为什么启动时要从 Chroma 重建 BM25？

BM25 是纯内存索引，重启即丢失。不重建则混合检索静默退化为向量单路——不报错、不 500，只是效果变差，极难排查。

06为什么提示词单独放一个模块？

提示词是「配置资产」不是代码逻辑。集中管理才能锁版本、控制实验变量——跑 Baseline vs Adaptive 对比时，锁不住版本，对比数字就不可信。

07为什么评测和线上共用一个入口？

编排逻辑只有一份，接口层只做交付格式适配。两套实现的系统，评测数字没有参考价值；共用入口才能让评测和线上永不脱节。

08为什么 Critic 故障时选择 fail-open？

误拒一篇合格回答的成本高于漏放一篇（主防线已过、有引用可查）。但降级行为必须进 trace 的 degraded 字段——任何降级都必须是显式的。

Honest Limitations & Roadmap

已知限制，比成绩单更能说明工程能力

这一节完整保留：哪些是当前实现的真实边界，哪些是下一步的优化动作。

已知限制

  1. BM25 全量重建：rank_bm25 不支持增量更新，十万级 chunk 以上需换 ES / OpenSearch。
  2. BM25 0 分候选未过滤：无词项命中仍返回 top_k，当前靠精排阈值守门。
  3. 体验层流式：当前是「算完再推」的打字机效果，非 LLM token 级流式。
  4. chunk 粒度粗：500 字固定窗口，一条 FAQ 仅百余字，导致单 chunk 塞入 5-6 条问答。
  5. 精排延迟高：CPU 上逐条打分，P50 被拉高到 24.8s，切小 chunk 是最优改动。
  6. 单机部署：SQLite + 本地 Chroma + 内存 BM25，未考虑多实例一致性。
